Final product & engineering specification

Enterprise Policy Agent

Eval-first portfolio project: проверяем, когда сильного RAG недостаточно для подготовки корректного access request и оправдан ли минимальный deterministic decision workflow.

Версия 2.0 Статус: Ready for Gate 0 Назначение: portfolio proof-of-method Контур v1: read-only
Главное ограничение. Проект не использует внутренние данные реальной компании и не имеет IAM/Security SME как production reference. Поэтому он может доказать качество метода на публичном реалистичном policy pack, но не готовность к enterprise deployment, production safety или экономический эффект у клиента.

0. Решение в одном экране

Система помогает сотруднику подготовить запрос на standard, privileged или temporary access. Она извлекает факты из естественного языка, отделяет сообщённые пользователем данные от доверенных атрибутов, находит применимые правила, задаёт минимально необходимое уточнение и выдаёт проверяемый следующий шаг. В v1 система не одобряет доступ и ничего не записывает во внешние системы.

Исходная гипотеза не состоит в том, что «агенты лучше». Проверяется более узкий тезис: structured extraction + deterministic policy evaluation устраняют критичные ошибки сильного RAG и окупают дополнительную сложность. Если strong RAG либо form + runbook достигают практически эквивалентного результата, гибридная архитектура не принимается.

Request→ Trusted context→ Allowed evidence→ Partial policy evaluation→ Clarify / Decide / Escalate

Definition of success

На закрытом final test минимальный гибрид должен превзойти strong RAG по full-decision correctness минимум на 5 процентных пунктов либо устранить заранее выбранный класс критичных ошибок при отсутствии ухудшения остальных safety gates. Результат должен сохраняться на raw-policy slice, а стоимость подготовки данных должна быть раскрыта.

Definition of failure

Гипотеза отвергнута, если простой baseline достигает не менее 95% качества гибрида, не допускает дополнительных критичных ошибок и существенно дешевле по latency, inference cost и maintenance effort. Результат объявляется INCONCLUSIVE, если данных недостаточно для вывода; отсутствие доказанного нулевого эффекта не считается улучшением.

1. Продуктовая гипотеза

Проблема

Неформальная просьба «дайте доступ» должна превратиться в запрос, который можно обработать: известны субъект, ресурс, операция, уровень, длительность и обоснование; найдены обязательные правила; определены согласующие; неизвестные доверенные факты не додуманы. Обычный поиск требует от сотрудника знания терминов. Обычный RAG способен объяснить документы, но может нестабильно применять составные условия, пропускать обязательное исключение и принимать self-reported факты за авторитетные.

Пользователи и JTBD

Security/AdminПолучить проверяемый draft решения с evidenceМеньше повторного поиска и ручной классификации

Проверяемые гипотезы

  1. H1 — Decision quality. Гибридный workflow лучше strong RAG определяет полный decision contract.
  2. H2 — Sufficiency. Partial policy evaluation уменьшает premature answers без избыточных уточнений.
  3. H3 — Reproducibility. Deterministic rules уменьшают variance только при одновременном сохранении correctness.
  4. H4 — Data cost. Прирост качества остаётся оправданным с учётом ручной нормализации и сопровождения rules.

Agentic hypothesis отсутствует в v1. Planner, reflection, multi-agent и dynamic tool selection не входят в решение, пока фиксированный workflow не покажет конкретный непреодолимый failure mode.

2. Scope, ограничения и non-claims

Входит

  • Один coherent access-request policy pack
  • Standard, privileged, temporary как независимые признаки
  • Single-turn и короткий clarification flow
  • Read-only decision support
  • Public, versioned raw sources
  • Blind final evaluation

Не входит

  • Одобрение или выдача доступа
  • Jira, ServiceNow, IdP writes
  • Planner, critic, memory, multi-agent
  • Универсальный ingestion
  • Production IAM integration
  • Доказательство экономического ROI

Не заявляем

  • Production-ready security
  • Нулевую вероятность утечки
  • Переносимость на любую компанию
  • Human-level quality
  • Реальное сокращение approval cycle
  • Необходимость agent architecture

Minimum credible v1

Полный вертикальный срез: исходный запрос → доверенный identity/resource snapshot → raw policy evidence → уточнение при необходимости → применимые правила → обязательные approvals → следующий шаг → разрешённое объяснение с citations. Система поддерживает только условия, представимые утверждённой v1 rule schema; неподдерживаемое условие обнаруживается и ведёт к эскалации.

3. Trust model и decision contract

Каждый факт хранится вместе с происхождением. Текст пользователя не является источником полномочий.

Класс фактаПримерДопустимый источникЕсли источник отсутствует
Self-reportedЦель, требуемая длительность, бизнес-обоснованиеUser inputУточнить у пользователя
Authoritative identityРоль, подразделение, employment statusFrozen identity snapshotEscalate: UNVERIFIED_IDENTITY
Authoritative resourceOwner, environment, sensitivityVersioned resource catalogEscalate: UNKNOWN_RESOURCE
Authorization eventManager approval already grantedSigned event in approval fixtureСчитать approval отсутствующим
Policy factApproval requirements, duration capEffective source document / verified ruleEscalate: NO_POLICY

Три разных отношения к policy

  • policy_applies_to_subject — правило влияет на решение.
  • principal_can_read_policy — пользователь может видеть текст и идентификатор.
  • principal_can_receive_outcome — пользователю можно сообщить безопасный результат без закрытых деталей.

Недоступная пользователю policy может быть обязательной. В portfolio v1 такие правила оценивает доверенный deterministic layer; генератор получает только разрешённую проекцию решения. Если безопасную проекцию невозможно построить, система эскалирует без раскрытия существования или содержания закрытого ресурса.

4. Четыре принципиально разных подхода

A. Strong raw RAG

Разрешённые raw documents → retrieval → frontier LLM → structured answer.

Плюсы: минимальная разработка, работает с естественным языком.

Минусы: труднее гарантировать составные условия, полноту и повторяемость.

Роль: главный AI baseline.

B. Form + runbook

Структурированная форма → deterministic checklist/rules → template response.

Плюсы: воспроизводимость, низкая стоимость, прозрачность.

Минусы: хуже переносит естественный язык и неизвестные формулировки.

Роль: главный non-LLM baseline.

C. Minimal hybrid

LLM extraction → trusted-fact merge → deterministic policy engine → constrained explanation.

Плюсы: язык обрабатывает LLM, authority остаётся в правилах.

Минусы: стоимость нормализации и сопровождения rule schema.

Вердикт: рекомендуемый кандидат, только если пройдёт gates.

D. Agentic lookup

Модель динамически планирует поиск по связанным источникам и выбирает инструменты.

Плюсы: потенциально полезен для неизвестных multi-hop зависимостей.

Минусы: variance, latency, attack surface, сложная атрибуция эффекта.

Вердикт: deferred; не реализуется в v1.

Общий интерфейс сравнения

Все подходы получают один и тот же case fixture, policy snapshot, model family там, где нужна LLM, общий token/time budget и одинаковую safety envelope. Подходы различаются только тестируемым механизмом. Нормализация рассматривается как отдельная экспериментальная ось, а не бесплатное преимущество гибрида.

5. Corpus, normalization и eval dataset

Gate 0 — corpus feasibility

До написания application code выбирается один публичный coherent policy family одной организации или открытого reference implementation. Набор должен содержать правила запроса доступа, классификацию ресурсов, approval logic и хотя бы два формата документов. Смешивать правила разных организаций для видимости масштаба запрещено.

Если публичный набор не позволяет однозначно вывести approvals, scope сужается до request completeness and policy applicability. Недостающая approval matrix не создаётся и не выдаётся за enterprise fact.

Normalization protocol

Raw artifact→ Parsed text + structure→ Atomic requirements→ Rule schema→ Boundary tests

Каждое атомарное правило содержит source span, effective date, scope, conditions, exceptions, priority и статус неоднозначности. Нормализатор не имеет доступа к закрытому final test.

Пять документов — discovery sample. Они не доказывают масштабируемость ingestion. При провале fidelity проект сужает поддерживаемый corpus либо получает NO-GO; автоматический universal ingestion не добавляется по умолчанию.

Разделение выполняется по semantic case family. Перефразы, переводы и варианты одного boundary condition остаются в одном split. После раскрытия final labels любые изменения создают новую major dataset version и требуют нового закрытого test set; прежняя оценка сохраняется.

Обязательные slices

  • Standard / privileged × permanent / temporary; privileged и temporary не взаимоисключающие классы.
  • Requester ≠ beneficiary; запрос доступа «как у коллеги»; spoofed role; исправление ранее сообщённого факта.
  • Missing self-reported fact; missing authoritative fact; unknown resource; absent policy.
  • Multiple applicable policies; explicit override; unresolved conflict; stale/superseded document.
  • Irrelevant distractors; duplicate content; long table; cross-lingual query; noisy terminology.
  • Answerable, clarification-required, escalation-required, forbidden-disclosure и out-of-scope cases.

Annotation без IAM SME

Gold создаётся только там, где решение выводимо из публичных источников и формальных fixtures. Два независимых прохода выполняются автором в разные моменты по versioned guide; disagreement сохраняется. Для critical labels обязателен source span и executable boundary test. Неоднозначные случаи получают acceptable alternatives либо ESCALATE.

Это не заменяет SME. Метрики IAA и «human baseline» не заявляются. Опциональное внешнее review может усилить проект, но отсутствие review не скрывается.

6. Experiment design и ablations

Pre-implementation validation pack

  1. Выбрать corpus и пройти Gate 0.
  2. Нормализовать 3–5 raw artifacts; выполнить fidelity review.
  3. Создать 15 micro-eval cases: минимум 4 missing-info, 3 role-sensitive, 3 multi-policy и 3 negative/out-of-scope.
  4. Запустить A: strong raw RAG и B: form + runbook.
  5. Составить first error table. До этого candidate failures не называются observed problems.

Fair comparison

  • Одинаковые policy snapshot, trusted fixtures и disclosure constraints.
  • Одна model/version и сопоставимый context budget для LLM-вариантов.

7. Метрики и go/no-go gates

9. Security, ACL и adversarial eval

Enforcement boundary

  • Identity и permissions приходят из signed/versioned fixture, не из prompt.
  • ACL применяется до LLM context и повторно перед формированием citations.
  • Cache key включает principal, permission snapshot и corpus version.
  • Rule engine работает с trusted representation; LLM не меняет approvals и authority facts.
  • Retrieved documents считаются данными, а не инструкциями; tool calls отсутствуют в v1.
  • Trace хранит необходимые идентификаторы и hashes; forbidden content не копируется в user-visible logs.

LLM judge и human review

LLM judge используется только для clarity/readability: pairwise, blind labels, randomized order, tie option и swap check. Он не оценивает authority, ACL, approvals, missing critical facts и safety.

Structured equality, policy IDs, permissions, state и forbidden terms проверяются детерминированно. Semantic support claim → source span проверяется вручную на стратифицированной выборке минимум 30 ответов и на всех critical failures. Reviewer не видит названия варианта. Поскольку SME отсутствует, вывод формулируется как source-grounded annotation review, не expert IAM validation.

Partial evaluation

Rule engine не собирает объединение всех slots всех найденных policies. Он вычисляет достижимые ветви при известных фактах и выбирает вопрос с максимальной способностью различить допустимые outcomes. Если требуемый факт authoritative, система не спрашивает пользователя, а выполняет lookup или эскалирует.

Full-text retrieval допускается только если corpus не помещается в установленный context budget либо baseline показывает пользу retrieval. Для малого normalized corpus evaluator может работать без vector database.

12. Этапы, артефакты и acceptance criteria

Milestone 0 — Evidence pack

  • Выбран один coherent public corpus и сохранён manifest с hashes.
  • Зафиксированы supported decision questions и non-claims.
  • Созданы provenance, identity и resource fixtures.
  • Пройден normalization fidelity discovery.
  • Micro-eval выявил observed error classes E0/E2.

Milestone 1 — Baseline report

  • Реализованы E0 strong raw RAG и E2 form + runbook.
  • Все версии prompts/models/corpus/dataset фиксируются.
  • Есть per-case traces и error taxonomy.
  • Gate G1 решён: STOP, продолжить RAG или строить E3.

Milestone 2 — Decision v1

  • E1/E3 и oracle ablations реализованы только для наблюдаемых ошибок.
  • Каждый оставленный компонент имеет KEEP experiment.
  • Closed final test запущен один раз после freeze.
  • Опубликованы absolute counts, paired CIs, slices и failed cases.
  • Safety zeros сопровождаются знаменателями и coverage.
  • README показывает data-preparation и maintenance cost.
  • Working demo воспроизводит минимум DECIDE, CLARIFY, ESCALATE и protected-policy case.

Milestone 3 — Portfolio case study

  • Problem → baselines → errors → single changes → results показаны в одной таблице.
  • Есть минимум один REVERT/STOP либо честное объяснение, почему все changes прошли.
  • Отдельно показано, сколько улучшения дала нормализация и сколько decision engine.
  • Написан раздел «что этот эксперимент не доказывает».
  • Agentic architecture отсутствует либо подкреплена отдельным preregistered experiment.

Стоп-критерии

  • Нет coherent public corpus, из которого можно вывести gold без выдуманной approval matrix.
  • Normalization critical fidelity не проходит после одного пересмотра schema.
  • Strong RAG проходит target и safety gates; specialized layer не решает отдельный observed error.
  • Прирост E3 неотличим от эффекта нормализации либо остаётся статистически неопределённым.
  • Scope начинает требовать production IAM, write integration или universal ingestion для доказательства H1.
